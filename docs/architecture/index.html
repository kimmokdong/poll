README.md

마음신호 프로젝트 해부도

프로젝트를 한 문장과 한 장의 그림으로 먼저 이해합니다.

바이브코딩 입문자를 위한 실제 코드 기반 구조 안내서입니다. 게임 사용법은 기존 사용설명서, 코드를 이해하고 수정할 위치는 이 문서 묶음에서 찾으세요.

한 화면에서 읽기: 프로젝트 구조·실행 흐름 통합 HTML에서 아래 10개 문서와 9개 다이어그램을 검색하며 한 번에 볼 수 있습니다.

  • 조사 기준일: 2026-08-31
  • 조사 대상: 현재 로컬 poll-main 폴더의 실행 코드, 설정, 테스트, 설명서, 발표자료 및 생성물 구조
  • 원칙: 기존 기능 코드·배포 설정은 변경하지 않았습니다. 환경변수 값, PIN, 인증 토큰, 로컬 방 데이터는 수록하지 않았습니다.
  • 근거 표현: 확인은 코드·설정·실행 검사로 확인한 내용, 확인 필요는 원격 계정이나 운영 환경을 추가 조사해야 하는 내용입니다.

이 프로젝트를 한 문장으로 설명하면

“이 프로젝트는 교사와 학생이 학급 투표·예측·추리 게임을 하고 교실 TV로 진행 상황을 함께 볼 수 있도록 만든 실시간 웹 애플리케이션이며, 프론트엔드는 HTML·CSS·순수 JavaScript, 백엔드는 Cloudflare Worker와 방별 Durable Object, 데이터 저장은 SQLite 기반 Durable Object Storage의 키-값 API, 배포는 Cloudflare Workers와 Static Assets를 사용하는 구조이다.”

처음 보는 사람을 위한 전체 흐름

  1. 교사와 학생은 같은 public/index.html을 열지만, public/app.js가 초대 링크·5자리 코드 입장과 로그인 상태를 보고 서로 다른 화면을 만듭니다.
  2. 교실 TV는 별도의 public/display.html과 public/display.js를 사용합니다.
  3. 버튼을 누르면 브라우저의 이벤트 처리 코드가 같은 서비스 주소의 /api/...로 JSON 요청을 보냅니다.
  4. Cloudflare에서 실행되는 src/worker.js가 주소를 읽고 해당 방을 담당하는 Room Durable Object로 요청을 전달합니다.
  5. 방 코드는 ROOMS.idFromName(code)를 통해 항상 같은 방 객체를 찾는 열쇠로 사용됩니다.
  6. src/game.js는 투표 가능 단계, 예측, 토큰, 점수 등의 규칙을 검사하고 방 객체를 바꿉니다.
  7. 서버는 바뀐 방 객체를 ctx.storage.put('room', room)으로 저장한 다음, 각 화면에 필요한 정보만 골라 WebSocket으로 보냅니다.
  8. 브라우저는 확정된 서버 상태와 아직 작성 중인 입력값을 구분해 화면을 갱신합니다. 화면 타이머는 브라우저에서 움직이므로 매초 API를 조회하는 구조가 아닙니다.
  9. 앱은 클라우드에 배포되지만 개발자의 PC에서는 Node.js와 Wrangler로 실행·테스트·빌드합니다.
  10. README에는 GitHub 연결 안내가 있으나, 현재 폴더의 .git과 자동 배포 워크플로는 없어 실제 GitHub 연동 여부는 확인 필요입니다.

전체 시스템 아키텍처

교사·학생·TV 화면, Worker, 게임 규칙, 저장소의 연결을 봅니다.

문서 첫 화면 · 기준일 2026-08-31

1. 실제 실행 구조

브라우저에서 보이는 화면, Cloudflare에서 실행하는 코드, 방 데이터를 보관하는 저장소는 서로 다른 역할입니다. 이 프로젝트에서는 하나의 Worker 배포가 정적 화면과 API를 함께 제공합니다.

이 그림의 저장소는 Cloudflare D1이나 Workers KV 서비스가 아닙니다. wrangler.jsonc가 Room을 SQLite 기반 Durable Object 클래스로 만들고, 실행 코드는 SQL 쿼리 대신 Storage의 키-값 API를 사용합니다. SQLite 기반 DO에서도 키-값 API를 사용할 수 있다는 플랫폼 설명은 Cloudflare Storage 문서와 일치합니다.

2. 구성요소의 역할

구성요소 실제 사용 기술 또는 플랫폼 역할 관련 코드 위치 입문자가 알아둘 개념
교사·학생 웹 입구 HTML JavaScript와 CSS를 불러오고 화면을 담을 요소 제공 public/index.html HTML 자체에는 전체 화면이 미리 들어 있지 않음
교사·학생 화면 순수 JavaScript 역할·단계별 HTML 문자열, 폼, 버튼, 세션 처리 public/app.js: render, teacherView, studentView 화면 함수가 이 프로젝트의 컴포넌트 역할
TV 화면 별도 HTML·JS·CSS 공개 진행·결과와 음향 연출 public/display.* 같은 데이터를 다른 개인정보 범위로 표시
게임 API 입구 Cloudflare Worker 경로 분기, 요청 크기·JSON 검사, 방 객체 전달 src/worker.js: fetch, api, readJson 서버리스 HTTP 핸들러
방별 서버 Durable Object Room 인증, 방 불러오기, 저장, WebSocket, 알람 src/worker.js: Room 방 코드 하나가 상태를 소유하는 객체 하나를 찾음
게임 규칙 서버 JavaScript ES module 모드·단계·투표·예측·승리·점수 결정 src/game.js 브라우저에서 임의로 점수를 결정하지 않음
영구 저장소 DO 내부 SQLite 기반 Storage 방 객체 전체를 room 키에 보관 Room.loadRoom, persist, expire 관계형 DB 엔진 위에서 객체를 키-값 형태로 저장
실시간 연결 WebSocket Hibernation API 서버에서 각 연결로 최신 상태 전송 acceptWebSocket, broadcast, webSocketMessage Socket.IO·SSE가 아니라 기본 WebSocket
브라우저 로컬 저장 localStorage·Map 재입장용 세션, TV 설정, 미제출 초안 readSession, saveSession, formDrafts 서버 데이터의 대체 저장소가 아님
정적 캐시 Service Worker Cache API 네트워크 실패 시 일부 화면 자산 재사용 public/sw.js API 데이터와 오프라인 투표는 저장하지 않음
빌드·업로드 Node.js·Wrangler .dist 생성, Worker와 정적 자산 배포 scripts/build-assets.js, package.json 빌드는 배포 준비, 배포는 클라우드 업로드
사용설명서 자체 HTML·CSS·JS 역할별 사용 흐름·이미지 확대 manual/index.html 앱 API와 독립적인 정적 교육자료

버튼에서 저장소까지: 실제 실행 흐름

버튼을 누른 뒤 저장·방송·화면 갱신까지의 실제 순서를 따라갑니다.

문서 첫 화면 · 기준일 2026-08-31

1. 먼저 알아둘 공통 규칙

  • 화면에서 버튼을 눌렀다고 서버 데이터가 바로 바뀌는 것은 아닙니다. 브라우저가 요청하고, 서버가 권한·단계를 검사하고, 저장한 뒤 응답합니다.
  • 교사·학생의 게임 명령은 public/app.js의 action → api를 거칩니다. 서버에서는 src/worker.js의 api → Room.fetch가 받고 src/game.js가 규칙을 적용합니다.
  • 상태 변경 뒤에는 HTTP 응답과 WebSocket 방송 양쪽에서 최신 상태를 받을 수 있습니다. 이것은 같은 투표를 두 번 저장하는 구조와는 다릅니다.
  • 아래의 :code는 방 코드 자리표시자입니다. 인증정보는 종류만 표시하며 실제 값을 싣지 않습니다.

2. 대표 흐름 ① 교사가 학급방을 만든다

  1. HTML에 고정된 관리 화면이 있는 것이 아니라 authScreen()이 만든 폼을 document의 submit 이벤트가 받습니다.
  2. Worker는 후보 방 코드를 만들어 같은 이름의 Durable Object를 찾습니다. 기존 방과 충돌하면 다른 코드를 시도합니다.
  3. createRoom()은 서버 원본 객체를 만들고, 응답은 필요한 필드만 담습니다. 평문 PIN을 방 객체에 저장하지 않고 salt와 해시를 저장합니다.
  4. saveSession()은 이 브라우저가 다시 관리 화면을 열 수 있도록 세션을 localStorage에 남깁니다.
  5. 기존 방 로그인은 별도 teacher-login-form에서 POST /api/rooms/:code/teacher-login을 보냅니다. PIN 검증 성공 시 교사 토큰을 새로 발급하므로 이전 교사 토큰은 더 이상 유효하지 않습니다.

근거: public/app.js의 authScreen, 제출 이벤트; src/worker.js의 api, Room.fetch; src/game.js의 createRoom, roomCode, pinHash.

3. 대표 흐름 ② 학생이 초대 링크로 들어오고 재접속한다

deviceToken은 별도 하드웨어 식별자가 아니라 이전에 발급받은 학생 세션 토큰을 재입장 요청에서 부르는 이름입니다. 같은 토큰을 제시하면 기존 학생을 찾지만, 토큰이 없으면 이름이 같아도 새 학생으로 등록될 수 있습니다.

연결과 명단은 분리되어 있습니다.

상황 서버 처리 화면·집계 영향
학생의 마지막 소켓 종료 handleSocketDeparture가 lastSeen/disconnectedAt 저장 online 표시가 꺼지지만 등록된 학생 자체는 남음
연결 종료 후 유예 기간 안 activePlayerIds가 30초간 참여 상태 유지 잠깐 끊긴 학생 때문에 즉시 라운드 인원이 바뀌지 않음
유예가 지난 뒤 알람·상태 계산에서 현재 활동 인원 제외 완료 대기 인원에서 빠짐. 기존 표·점수의 삭제와는 다른 처리
기존 토큰으로 복귀 연결 수락 때 disconnectedAt = null 같은 학생으로 다시 연결; 현재 라운드 참가자였으면 복귀 가능
라운드 시작 후 새로 등록 참가자 스냅샷에 없음 이번 라운드는 관전, 다음 라운드부터 참여
교사가 X로 삭제 remove_player가 room.players에서 삭제 재연결 유예가 아니라 명단 삭제. 기존 표 처리 정책은 위험요소 참고

restore()는 현재 네트워크 오류도 인증 실패처럼 세션을 지우는 경로가 있습니다. 위 정상 흐름이 모든 장애 상황을 복구한다는 뜻은 아닙니다.

4. 대표 흐름 ③ 라운드를 시작하고 학생이 투표한다

  • autoAdvance를 끄면 시간 만료 자체가 단계 전환을 강제하지 않습니다. 화면 시간이 0이 됐다는 사실과 서버의 제출 가능 단계가 끝났다는 사실을 구분해야 합니다.

5. 대표 흐름 ④ 표심전에서 예측하고 점수 내역을 받는다

서버는 최종 예측이 없으면 기존 1차 예측을 채점에 사용할 수 있습니다. 다만 1차 예측 자체를 건너뛴 학생이 최종 단계에서 처음 제출하는 경우는 현재 거절됩니다. 예측 미제출 시 토큰 점수까지 어떻게 처리되는지도 scoreRound가 정하며, 단순히 화면의 점수 안내만 바꿔서는 규칙이 바뀌지 않습니다.

scoreRound()의 scored는 같은 라운드 점수의 중복 가산을 막는 플래그입니다. 이것이 모든 API의 중복 요청을 막는 범용 장치는 아닙니다.

데이터베이스와 상태 보관 방식

방·학생·투표·점수가 어떤 모양으로 어디에 저장되는지 설명합니다.

문서 첫 화면 · 기준일 2026-08-31

1. 결론: 방마다 하나의 객체를 영구 저장한다

이 프로젝트에는 백엔드 저장소가 있습니다. Cloudflare의 SQLite 기반 Durable Object Storage를 사용하지만, 앱이 SQL 테이블을 직접 만들거나 조회하지는 않습니다.

방 코드
  → env.ROOMS.idFromName(code)
  → 그 방을 담당하는 Room Durable Object
  → ctx.storage
  → 키 'room' 하나에 방 객체 저장
질문 실제 답 코드 근거
어느 플랫폼인가? Cloudflare Durable Objects wrangler.jsonc: ROOMS, class_name
내부 DB 엔진은? SQLite 기반 DO 클래스 같은 설정의 new_sqlite_classes
앱의 접근 방식은? get/put/deleteAll 키-값 API src/worker.js: loadRoom/persist/expire
관계형인가, 문서형인가? 기반 엔진은 관계형 SQLite, 앱의 모델은 중첩 객체를 담는 키-값 방식 SQL 쿼리·ORM·사용자 정의 테이블 없음
테이블이나 컬렉션 이름은? 앱이 정의한 테이블·컬렉션 없음. 실제 키는 room ROOM_KEY
D1인가? Workers KV인가? 둘 다 아님. DO Storage의 KV API를 쓰는 것 D1/KV 바인딩 없음

브라우저가 직접 DB를 읽는가? 아니요. Worker → Room을 거침 public/app.js: api / src/worker.js

SQLite 기반 DO의 키-값 데이터는 플랫폼 내부 저장 구조를 사용합니다. 이를 근거로 이 앱에 users, votes 같은 SQL 테이블이 있다고 설명해서는 안 됩니다. Cloudflare Storage 문서

2. 논리적인 데이터 관계

아래 ER 도식의 상자는 실제 객체와 하위 객체입니다. 물리적인 SQL 테이블, 외래키 제약, 독립적인 컬렉션이 아닙니다. 이름을 짧게 붙여 관계를 이해하기 쉽게 표현했습니다.

인증 관련 필드는 그림에서 생략했습니다. 필드 이름과 쓰임은 아래에 설명하지만 실제 값은 수록하지 않습니다. currentRound, timerEnd, capacity 등은 상황에 따라 null일 수 있습니다. disconnectedAt은 처음 등록할 때 항상 생성되는 필드가 아니라 연결/해제 과정에서 추가됩니다. 한 라운드의 보기는 실제로 2~6개이며 ER의 일반적인 ‘여러 개’ 표기보다 서버 검증이 더 구체적입니다.

5. 서버 원본과 화면 응답은 다르다

clientState()와 displayState()는 원본 데이터를 역할에 맞게 가공합니다. 이 응답을 DTO, 즉 ‘전달용 데이터 형태’라고 부를 수 있습니다.

응답 필드 어디에서 계산하는가 원본과의 차이
serverTime 응답 생성 시 Date.now() 저장된 게임 필드 아님
online 현재 소켓의 토큰 목록 저장된 boolean을 읽는 것이 아님
roundActive, totalPlayers, totalTeams 참가자 스냅샷 + 현재 연결/유예 등록된 학생 수와 다를 수 있음
submissions 활동 참가자의 제출 여부 방 전체 제출 객체의 단순 길이와 다름
results publicResults 공개 방식·진행 단계·역할에 따라 필터
myVote, prediction, skillState, mission 현재 학생 ID로 조회 다른 학생의 비밀 선택/정보는 전달하지 않음
myPoints, pointBreakdown 채점 완료 후 본인 항목 점수 내역을 개인 화면에 제공
teamScores 모든 등록 학생의 누적 점수 합산 팀 모드가 아닌 때에도 API 응답에는 존재
TV의 players 이름·ID 등을 제거한 { online } 목록 TV에 학생 명단을 그대로 전달하지 않음

DB 권한은 Firestore Rules 같은 별도 파일이 아니라 authenticate, 교사/학생 명령 분리, 단계 검증, 응답 필터에서 구현됩니다. 화면에서 버튼을 숨기는 것만으로 권한을 제한하는 구조는 아닙니다.

6. 데이터가 언제까지 남는가?

  • 방 전체의 만료 기준은 ROOM_TTL_HOURS를 읽는 Room.ttlMs()가 정합니다. 이 문서에는 설정값을 싣지 않습니다.
  • 방 생성·로그인·입장·인증 상태 조회·action·WebSocket 연결 수락에서 touch()로 활동 및 만료 시각을 갱신합니다.
  • 이미 열린 소켓의 ping/pong과 공개 TV 상태 조회만으로 touch()가 호출되는 것은 아닙니다. ‘TV가 켜져 있음’과 ‘방 만료가 계속 연장됨’을 동일하게 보면 안 됩니다.
  • expire()는 해당 방 DO의 저장 데이터를 지웁니다. 별도의 영구 학생 계정, 장기 성적표, 백업 내보내기 기능은 현재 코드에서 확인되지 않았습니다.
  • 새 라운드는 currentRound를 교체합니다. 개인 표·예측·토큰 사용·점수 세부 내역 전체가 여러 라운드 이력으로 보관되는 구조는 아닙니다.
  • finishRound()는 집계 결과 요약을 history에 최대 20개 보관합니다. 교사 응답에는 최근 5개만 포함되고 현재 기록 UI는 연결되어 있지 않습니다.
  • advanceRound()로 finished에 도달하는 경로는 finishRound()와 같지 않아 기록 생성이 다릅니다. 장기 보관이나 감사 기록이 필요하면 별도 정책이 필요합니다.

7. 브라우저와 로컬 개발 환경의 저장소

저장 위치 보관 내용 브라우저를 닫거나 새로고침하면?
교사·학생 localStorage 방 코드·역할·세션 토큰, 학생 이름 일반적으로 남음. 나가기/저장소 삭제/현재 복원 실패 처리로 지워질 수 있음
TV localStorage BGM 음량, 방 코드 숨김 설정 같은 브라우저에 남음
app.js의 state 서버가 보낸 최신 상태 메모리이므로 페이지 재시작 때 다시 조회
formDrafts Map, draftOptions 미제출 폼·보기·선택 초안 같은 페이지의 재렌더링에는 복구하지만 새로고침 복구 보장은 없음
sw.js의 Cache API 일부 HTML·CSS·JS·이미지 캐시가 남아도 오프라인 투표를 저장·전송하는 기능은 없음
.wrangler/state/ Wrangler 로컬 개발용 상태 운영 Cloudflare 저장소와 별개. 실제 방 데이터 내용은 조사하지 않음

sessionStorage, IndexedDB, 운영용 data/rooms.json 저장 코드는 없습니다. .wrangler 안에 SQLite 관련 파일이 있다는 사실을 ‘운영 서버가 내 PC의 DB 파일을 쓴다’고 해석하면 안 됩니다.

8. 입문자가 자주 묻는 질문

서버와 DB는 같은 것인가? 아니요. Room의 코드는 요청을 검사·계산하고, Storage는 데이터를 보관합니다. 같은 Cloudflare 플랫폼 안에 있어도 역할은 다릅니다.

브라우저를 닫으면 표도 없어지는가? 이미 서버에 저장된 표는 브라우저 종료만으로 사라지지 않습니다. 다만 방 만료·새 라운드 교체·삭제 정책에 따른 수명은 있습니다. 아직 제출하지 않은 입력은 별개입니다.

여러 사람이 동시에 같은 결과를 볼 수 있는가? 같은 방 DO가 저장한 상태를 각 연결에 WebSocket으로 전달하므로 가능합니다. 권한에 따라 전달하는 상세 정보는 다릅니다.

별도의 Firebase/Supabase 설정이 필요한가? 현재 구조에는 없습니다. 이 프로젝트의 저장소와 실시간 연결은 Cloudflare DO가 담당합니다.

localStorage에 토큰이 있으니 DB 키도 브라우저에 넣어도 되는가? 아닙니다. 학생/교사 세션 토큰과 플랫폼 관리자 비밀키는 권한 범위가 다릅니다. Cloudflare 배포 인증정보를 프론트엔드에 넣어서는 안 됩니다.

앱 사용자 인증

  • 교사는 새 방 생성 때 숫자 4자리 PIN을 정합니다. 서버는 salt와 SHA-256 해시를 보관합니다.
  • 기존 방에서는 PIN을 검증한 뒤 교사 토큰을 새로 발급합니다. 실패 횟수에 따른 짧은 잠금 처리가 있습니다.
  • 학생은 초대 링크에 포함된 방 코드 또는 메인 화면에 직접 입력한 5자리 코드와 이름으로 들어옵니다. 두 경로 모두 같은 입장 API를 사용하고, 서버가 학생별 불투명 토큰을 발급합니다. 별도 이메일 회원가입·비밀번호 계정은 없습니다.
  • HTTP 요청에서 브라우저는 Authorization: Bearer 방식으로 세션 토큰을 보냅니다. WebSocket 연결에서는 query 매개변수로 보냅니다.
  • authenticate()가 토큰을 검사하고, Room.fetch()가 교사/학생 action을 분리합니다. studentAction()은 참가자와 단계도 확인합니다.

토큰은 JWT가 아니며, Firebase Auth·Supabase Auth·Netlify Identity·OAuth를 학생 로그인에 사용하는 코드도 없습니다. 학생 본인 확인의 강도는 학교 계정 로그인과 같지 않습니다.

3. build는 무엇을 하는가?

scripts/build-assets.js의 실제 동작은 다음과 같습니다.

  1. 프로젝트 루트 아래의 .dist 경로인지 확인합니다.
  2. 기존 .dist 출력 폴더를 비웁니다.
  3. public/ 전체를 .dist/로 복사합니다.
  4. manual/index.html과 manual/assets/만 .dist/manual/로 복사합니다.

프론트엔드를 React/Vite로 컴파일하거나 CSS를 압축하는 스크립트는 아닙니다. Worker 서버 코드의 번들 처리는 Wrangler가 담당합니다.

원본 배포 결과 배포 여부
public/index.html, JS·CSS·manifest·SW·이미지 .dist/의 같은 경로 포함
manual/index.html .dist/manual/index.html 포함
manual/assets/ .dist/manual/assets/ 포함
src/worker.js, src/game.js Worker 서버 코드 정적 폴더 복사와 별도로 Wrangler가 배포
manual/qa, manual/sources, 제작 기록 없음 제외
260822_game_mode_guide/ 없음 제외
docs/architecture/ 없음 제외
test/, output/, .wrangler/ 없음 제외

따라서 .dist/app.js를 직접 수정하는 것은 지속적인 수정 방법이 아닙니다. 다음 build에서 원본으로 덮어씁니다. npm run dev의 복사 단계도 시작 시 한 번 실행되므로 public/ 변경이 화면에 보이지 않으면 원본과 .dist의 차이부터 확인하세요. 이 복사 스크립트 자체에는 지속 감시 기능이 없습니다.

5. GitHub에 push하면 자동 배포되는가?

현재 폴더 조사만으로는 확인할 수 없습니다.

확인된 사실:

  • 루트 README는 GitHub kimmokdong/poll의 main 브랜치를 Workers Builds에 연결하는 방식을 적고 있습니다.
  • README의 빌드/배포 안내는 npm run build, npx wrangler deploy입니다.
  • 현재 로컬 폴더에는 .git이 없고 Git 작업 트리로 인식되지 않습니다. .github/workflows도 없습니다.
  • Cloudflare 대시보드의 Build 연결, 원격 저장소, 최근 커밋·빌드 로그는 이번 범위에서 확인하지 않았습니다.

.github/workflows가 없다고 자동 배포가 반드시 없다는 뜻은 아닙니다. Workers Builds는 플랫폼 쪽 Git 연결로 동작할 수 있습니다. 연결된 경우에만 지정 브랜치 변경이 자동 빌드·배포로 이어집니다. Cloudflare Workers Builds 문서

추가 확인 순서는 Cloudflare의 해당 Worker → Settings/Builds 연결 → 저장소·브랜치·빌드 명령 → 최근 배포 로그입니다. 이 문서 작성 중에는 연결을 만들거나 설정을 바꾸지 않았습니다.

‘서버 슬립’과 WebSocket 휴면

이 프로젝트는 ctx.acceptWebSocket()과 attachment를 사용하는 DO Hibernation API 경로를 택했습니다. 플랫폼은 연결을 유지하면서 객체를 휴면시킬 수 있고, 필요할 때 다시 실행합니다. 따라서 메모리만 믿는 대신 storage.get('room')으로 상태를 읽는 구조가 중요합니다. Cloudflare WebSocket 휴면 문서

/sw.js HTTP 200, 내용 일치 public/sw.js
/manual/ HTTP 200, 내용 일치 manual/index.html

이 검사는 모든 자산, 서버 번들 버전, DB 상태, 자동 배포 설정이 같음을 증명하지 않습니다. 실제 교실방의 API를 열거나 데이터를 바꾸지 않았습니다. 현재 서버 배포 메타데이터, 커스텀 도메인, 별도 스테이징 환경은 확인 필요입니다.

8. 로컬과 운영이 달라지는 지점

  • 로컬 방 상태는 .wrangler/, 운영 방 상태는 Cloudflare DO에 있습니다. 로컬에서 테스트한 학생이 운영 명단에 들어가는 구조가 아닙니다.
  • 로컬 HTTP에서는 ws:, 운영 HTTPS에서는 wss:로 연결합니다. 주소는 프론트의 location에서 만듭니다.
  • 브라우저 Cache와 Service Worker가 이전 정적 파일을 보관할 수 있습니다. API는 no-store JSON 응답이고 Service Worker도 /api/를 제외합니다.
  • 노트북과 교실 TV는 브라우저·음향 허용·화면 크기·네트워크 조건이 다릅니다. 같은 서버 코드라도 현장 확인이 필요합니다.
  • 이 문서와 Mermaid 이미지는 현재 build 대상이 아닙니다. 운영 사용설명서에 게시하려면 별도 요청과 배포 범위 결정이 필요합니다.

코드와 연결해서 읽는 입문자 용어 사전

코드에서 만나는 핵심 용어를 이 프로젝트의 예로 풀이합니다.

문서 첫 화면 · 기준일 2026-08-31

프로젝트에 실제로 등장하는 개념만 설명합니다. 파일 경로는 프로젝트 루트 기준입니다. GitHub는 실행 연결이 확인된 기술이 아니라 기존 README에서 다루는 배포 관련 개념으로 구분했습니다.

프론트엔드

  • 쉬운 설명: 사용자의 브라우저에서 화면을 만들고 입력을 받는 부분입니다.
  • 이 프로젝트에서의 실제 예: teacherView()와 studentView()가 역할에 맞는 HTML을 만듭니다.
  • 관련 파일: public/index.html, public/app.js, public/styles.css, public/display.*.
  • 입문자가 흔히 오해하는 점: 화면에서 선택을 표시했다고 서버에 표가 저장된 것은 아닙니다.
  • 코드를 수정할 때 주의할 점: 안내 문구·버튼 활성화 조건이 서버의 실제 규칙과 맞아야 합니다.

백엔드

  • 쉬운 설명: 브라우저의 요청을 받아 권한을 확인하고 데이터를 계산·저장하는 부분입니다.
  • 이 프로젝트에서의 실제 예: Room.fetch()가 명령을 받고 studentAction()이 투표 규칙을 검사합니다.
  • 관련 파일: src/worker.js, src/game.js.
  • 입문자가 흔히 오해하는 점: 별도 server/ 폴더가 없어도 백엔드는 존재합니다.
  • 코드를 수정할 때 주의할 점: 화면에서 숨긴 버튼도 요청은 만들 수 있으므로 검증을 서버에 남겨야 합니다.

서버

  • 쉬운 설명: 다른 프로그램의 요청을 처리하는 역할 또는 그 실행 환경입니다.
  • 이 프로젝트에서의 실제 예: 운영에서는 Cloudflare의 Worker와 Room이 요청을 처리합니다.
  • 관련 파일: src/worker.js, wrangler.jsonc.
  • 입문자가 흔히 오해하는 점: 서버가 곧 데이터베이스나 개발자의 노트북을 의미하지는 않습니다.
  • 코드를 수정할 때 주의할 점: 운영은 일반적인 node server.js 상시 프로세스가 아니라 이벤트 실행 방식입니다.

클라이언트

  • 쉬운 설명: 서버에 요청하고 결과를 사용하는 프로그램입니다.
  • 이 프로젝트에서의 실제 예: 교사·학생·TV 브라우저는 같은 방을 서로 다른 권한으로 보는 클라이언트입니다.
  • 관련 파일: public/app.js, public/display.js.
  • 입문자가 흔히 오해하는 점: 모든 클라이언트가 같은 상태를 받아도 된다는 뜻은 아닙니다.
  • 코드를 수정할 때 주의할 점: 교사용 정보·개인 비밀 정보·TV 공개 정보를 구분해야 합니다.

API

  • 쉬운 설명: 프로그램끼리 요청과 결과를 주고받기로 정한 약속입니다.
  • 이 프로젝트에서의 실제 예: api()가 /api/rooms/:code/action에 명령과 payload를 보냅니다.
  • 관련 파일: public/app.js: api/action; src/worker.js: api, Room.fetch.
  • 입문자가 흔히 오해하는 점: API라고 해서 Google 같은 외부 회사의 서비스만 뜻하는 것은 아닙니다.
  • 코드를 수정할 때 주의할 점: 요청 형식이나 응답 필드를 바꾸면 보내는 쪽과 받는 쪽을 함께 확인합니다.

엔드포인트

  • 쉬운 설명: API에서 특정 처리를 요청하는 메서드와 주소의 조합입니다.
  • 이 프로젝트에서의 실제 예: POST /api/rooms는 방 생성, GET /api/rooms/:code/display-state는 공개 상태 조회입니다.
  • 관련 파일: src/worker.js: api, Room.fetch.
  • 입문자가 흔히 오해하는 점: /api 폴더가 있어야 API 주소가 생기는 것은 아닙니다.
  • 코드를 수정할 때 주의할 점: 같은 경로라도 GET·POST·WebSocket Upgrade가 서로 다릅니다.

요청과 응답

  • 쉬운 설명: 요청은 일을 시키는 메시지, 응답은 성공·실패와 결과를 돌려주는 메시지입니다.
  • 이 프로젝트에서의 실제 예: 학생 투표 요청 뒤 서버가 상태 JSON 또는 오류 JSON을 돌려줍니다.
  • 관련 파일: public/app.js: api; src/worker.js: readJson, json.
  • 입문자가 흔히 오해하는 점: 버튼 클릭 직후 UI가 반응했다고 저장 성공을 보장하지는 않습니다.
  • 코드를 수정할 때 주의할 점: 네트워크 실패와 권한 오류를 구분하고, 실패한 입력을 잃지 않도록 확인합니다.

JSON

  • 쉬운 설명: 이름과 값, 목록을 문자열로 표현하는 데이터 교환 형식입니다.
  • 이 프로젝트에서의 실제 예: { action, payload } 요청과 역할별 상태를 JSON.stringify/parse로 변환합니다.
  • 관련 파일: public/app.js, public/display.js, src/worker.js.
  • 입문자가 흔히 오해하는 점: JSON 응답 전체가 DB 원본과 같지는 않습니다.
  • 코드를 수정할 때 주의할 점: 숫자·문자열·boolean·null을 구분하고 PIN·다른 학생의 토큰을 응답에 섞지 않습니다.

데이터베이스

  • 쉬운 설명: 프로그램이 끝나거나 서버 실행 메모리가 사라져도 데이터를 보관하는 저장 장치입니다.
  • 이 프로젝트에서의 실제 예: DO Storage에 방 객체를 저장해 다음 요청에서 읽습니다.
  • 관련 파일: src/worker.js: loadRoom, persist, expire.
  • 입문자가 흔히 오해하는 점: JavaScript 변수 state는 DB가 아니며 localStorage도 서버 DB의 대체물이 아닙니다.
  • 코드를 수정할 때 주의할 점: 저장 데이터의 수명·삭제·기존 필드 호환성을 함께 생각합니다.

SQLite와 키-값 저장

  • 쉬운 설명: SQLite는 DB 엔진이고, 키-값 API는 이름 하나로 값을 저장·조회하는 접근 방식입니다.
  • 이 프로젝트에서의 실제 예: SQLite 기반 DO에서 storage.put('room', room)을 호출합니다.
  • 관련 파일: wrangler.jsonc의 new_sqlite_classes, src/worker.js의 ROOM_KEY.
  • 입문자가 흔히 오해하는 점: SQLite를 쓴다고 이 앱에 users·votes SQL 테이블이 있는 것은 아닙니다.
  • 코드를 수정할 때 주의할 점: 문서의 ER 도식은 하위 객체 관계이며 SQL 마이그레이션 명세가 아닙니다.

Durable Object

  • 쉬운 설명: 식별자별로 상태를 다루고 저장소를 갖는 Cloudflare의 서버 단위입니다.
  • 이 프로젝트에서의 실제 예: 방 코드를 ROOMS.idFromName(code)에 넣어 같은 방의 Room을 찾습니다.
  • 관련 파일: src/worker.js: roomStub, Room; wrangler.jsonc.
  • 입문자가 흔히 오해하는 점: 학생 한 명당 DO를 만드는 것이 아니라 현재 코드는 방별 DO를 사용합니다.
  • 코드를 수정할 때 주의할 점: 클래스·namespace 연결을 바꾸면 기존 저장 상태 접근과 마이그레이션을 검토해야 합니다.

인증과 권한

  • 쉬운 설명: 인증은 누구의 세션인지 확인하고, 권한은 그 세션이 무엇을 할 수 있는지 판단하는 일입니다.
  • 이 프로젝트에서의 실제 예: authenticate() 후 교사 명령과 학생 명령을 나눕니다.
  • 관련 파일: src/game.js: authenticate, teacherAction, studentAction; Room.fetch.
  • 입문자가 흔히 오해하는 점: 방 코드만 아는 것, 학생 토큰이 있는 것, 교사 토큰이 있는 것은 다른 권한입니다.
  • 코드를 수정할 때 주의할 점: 실제 토큰을 코드·스크린샷·문서에 넣지 말고 TV 공개 조회 범위도 함께 확인합니다.

상태 관리

  • 쉬운 설명: 지금 프로그램이 어떤 상황인지 기억하고 변경을 화면에 반영하는 방식입니다.
  • 이 프로젝트에서의 실제 예: 서버 방 객체, 브라우저 state, 작성 중 formDrafts가 서로 다른 상태를 맡습니다.
  • 관련 파일: src/game.js; public/app.js: receiveState, captureFormDraft, restoreFormDrafts.
  • 입문자가 흔히 오해하는 점: 서버에서 새 상태를 받았다고 아직 제출하지 않은 입력을 지워도 되는 것은 아닙니다.
  • 코드를 수정할 때 주의할 점: 방·라운드·단계가 같은지 확인하고 초안·포커스·스크롤 보존을 검사합니다.

컴포넌트

  • 쉬운 설명: 화면을 역할별로 나눠 만드는 단위입니다. 반드시 React 컴포넌트일 필요는 없습니다.
  • 이 프로젝트에서의 실제 예: roundForm, votePanel, predictionPanel, scoreReceipt는 HTML 문자열을 만드는 함수입니다.
  • 관련 파일: public/app.js, public/display.js.
  • 입문자가 흔히 오해하는 점: 함수마다 독립적인 DOM 수명이나 React식 상태가 자동 제공되지는 않습니다.
  • 코드를 수정할 때 주의할 점: render()가 innerHTML을 교체하는 구조와 상위 이벤트 위임을 함께 봅니다.

라우팅

  • 쉬운 설명: 주소나 상태에 따라 어떤 화면·처리를 선택할지 정하는 일입니다.
  • 이 프로젝트에서의 실제 예: Worker는 /display/:code를 TV HTML로, 앱은 linkedRoom과 세션을 학생 화면으로 연결합니다.
  • 관련 파일: src/worker.js: 기본 fetch; public/app.js: screen, render; wrangler.jsonc.
  • 입문자가 흔히 오해하는 점: 교사와 학생 화면이 다르다고 /teacher, /student라는 별도 주소가 있는 것은 아닙니다.
  • 코드를 수정할 때 주의할 점: Worker 경로 분기와 Static Assets 우선 처리 설정을 함께 확인합니다.

환경변수

  • 쉬운 설명: 코드 밖에서 실행 환경에 전달하는 설정입니다. 공개 설정과 비밀키는 구분해야 합니다.
  • 이 프로젝트에서의 실제 예: ROOM_TTL_HOURS로 방의 만료 기간을 읽습니다.
  • 관련 파일: wrangler.jsonc: vars; src/worker.js: ttlMs.
  • 입문자가 흔히 오해하는 점: 모든 환경변수가 비밀키인 것도, 모든 값이 브라우저에 전달되는 것도 아닙니다.
  • 코드를 수정할 때 주의할 점: 이름·용도·미설정 처리를 정하고 실제 비밀값을 public 파일에 넣지 않습니다.

바인딩

  • 쉬운 설명: 플랫폼 자원을 코드 안에서 사용할 수 있게 연결해 주는 이름입니다.
  • 이 프로젝트에서의 실제 예: env.ROOMS는 방 서버, env.ASSETS는 정적 파일을 찾는 객체입니다.
  • 관련 파일: wrangler.jsonc, src/worker.js.
  • 입문자가 흔히 오해하는 점: 바인딩은 같은 이름의 문자열을 .env에 넣어서 대신할 수 없습니다.
  • 코드를 수정할 때 주의할 점: 설정의 이름과 코드의 참조를 함께 맞춥니다.

빌드

  • 쉬운 설명: 소스에서 실행·배포에 쓸 결과물을 준비하는 과정입니다.
  • 이 프로젝트에서의 실제 예: Node 스크립트가 public과 배포용 manual을 .dist로 복사합니다.
  • 관련 파일: scripts/build-assets.js, package.json.
  • 입문자가 흔히 오해하는 점: npm run build만으로 운영 서버에 업로드되지는 않습니다.
  • 코드를 수정할 때 주의할 점: 출력 폴더를 직접 고치지 말고 원본을 수정하며, build가 .dist를 비운다는 점을 기억합니다.

배포

  • 쉬운 설명: 준비한 프로그램을 사용자가 접근할 실행 환경에 올리는 작업입니다.
  • 이 프로젝트에서의 실제 예: npm run deploy가 build 뒤 Wrangler로 Worker와 자산을 업로드합니다.
  • 관련 파일: package.json, wrangler.jsonc.
  • 입문자가 흔히 오해하는 점: 로컬 저장, Git 커밋, Git push, 운영 배포는 같은 작업이 아닙니다.
  • 코드를 수정할 때 주의할 점: 자동 배포 연결 여부를 확인하고, 실제 서비스 변경 전에 테스트·대상 계정을 점검합니다.

호스팅

  • 쉬운 설명: 프로그램과 파일을 사용자가 접근할 수 있도록 제공하는 운영 환경입니다.
  • 이 프로젝트에서의 실제 예: Cloudflare Workers와 Static Assets가 서비스 주소에서 앱을 제공합니다.
  • 관련 파일: wrangler.jsonc, src/worker.js.
  • 입문자가 흔히 오해하는 점: 호스팅 플랫폼 이름과 서버 코드의 언어는 같은 분류가 아닙니다.
  • 코드를 수정할 때 주의할 점: 화면 파일, 서버 로직, 저장 데이터 중 무엇을 바꾸는지 먼저 구분합니다.

CDN

  • 쉬운 설명: 여러 지역에서 정적 파일을 효율적으로 전달하도록 돕는 배포·캐시 계층입니다.
  • 이 프로젝트에서의 실제 예: Workers Static Assets가 HTML·CSS·JS·이미지를 전달합니다.
  • 관련 파일: wrangler.jsonc: assets; Room과 무관한 정적 파일 처리.
  • 입문자가 흔히 오해하는 점: CDN이 게임 점수를 계산하거나 학생 DB 역할을 하는 것은 아닙니다.
  • 코드를 수정할 때 주의할 점: 정적 파일 캐시와 /api/의 실시간 상태를 혼동하지 않습니다. 플랫폼 설명

서버리스와 휴면

  • 쉬운 설명: 개발자가 상시 서버 프로세스를 직접 관리하는 대신 플랫폼 이벤트로 코드를 실행하는 방식입니다.
  • 이 프로젝트에서의 실제 예: fetch, alarm, webSocketMessage가 요청·예약·소켓 메시지 때 호출됩니다.
  • 관련 파일: src/worker.js의 Worker와 Room 클래스.
  • 입문자가 흔히 오해하는 점: 서버가 없거나, 매 이벤트마다 저장 데이터가 초기화된다는 뜻은 아닙니다.
  • 코드를 수정할 때 주의할 점: DO는 휴면 후 메모리가 다시 만들어질 수 있어 영구 상태를 Storage에 둡니다. 플랫폼 설명

WebSocket과 실시간 전송

  • 쉬운 설명: 연결을 열어 두고 서버와 브라우저가 메시지를 주고받는 방식입니다.
  • 이 프로젝트에서의 실제 예: connect()로 연결하고 broadcast()가 각 역할의 최신 상태 JSON을 보냅니다.
  • 관련 파일: public/app.js, public/display.js, src/worker.js.
  • 입문자가 흔히 오해하는 점: 변수 이름이 eventSource여도 실제 구현은 SSE가 아니라 new WebSocket()입니다.
  • 코드를 수정할 때 주의할 점: 재연결·인증 만료·오프라인·동일 학생의 여러 탭을 함께 검사합니다.

Service Worker와 캐시

  • 쉬운 설명: 브라우저가 일부 요청을 중간에서 처리하고 파일을 보관할 수 있게 하는 기능입니다.
  • 이 프로젝트에서의 실제 예: sw.js는 정적 GET에서 네트워크를 먼저 사용하고 실패하면 캐시를 찾습니다.
  • 관련 파일: public/sw.js, 두 UI의 Service Worker 등록 코드.
  • 입문자가 흔히 오해하는 점: Service Worker는 Cloudflare Worker와 같은 코드가 아니며 오프라인 투표도 자동 제공하지 않습니다.
  • 코드를 수정할 때 주의할 점: /api/ 제외 정책을 유지하고 캐시 버전·자산 목록·구버전 화면 반영을 확인합니다.

패키지·라이브러리·의존성

Git

  • 코드를 수정할 때 주의할 점: 원격 연결을 추측해 push하지 말고 실제 저장소·브랜치·작업 트리를 먼저 확인합니다.

GitHub

2. 작은 화면 수정의 추천 순서

  1. 화면 문구나 data-action을 public/app.js 또는 public/display.js에서 찾습니다.
  2. 그 HTML을 만드는 함수와 적용된 class를 확인합니다. CSS는 같은 선택자의 뒤쪽 덮어쓰기도 찾습니다.
  3. 클릭/제출 이벤트에서 요청까지 이어지는지 확인합니다. 글자 변경과 게임 규칙 변경을 구분합니다.
  4. 원본만 수정합니다. .dist나 테스트 캡처를 실행 원본으로 고치지 않습니다.
  5. npm test로 기존 검사에 영향이 없는지 확인합니다.
  6. 로컬 build/dev로 실제 역할과 화면 크기를 확인합니다. 화면 검증 전에는 배포가 필요하지 않습니다.

DOM 전체 교체가 필요한지, 타이머·진행률의 숫자만 바꾸면 되는지를 구분하세요. 현재 코드는 초안·포커스·스크롤을 지키는 보완이 있으므로 이 경로를 무심코 우회하면 입력 초기화 문제가 다시 생길 수 있습니다.

3. 게임 규칙을 바꿀 때 반드시 맞출 네 곳

책임 실제 위치 예: 예측 배점을 바꾼다면
최종 계산 src/game.js scoreRound와 항목 내역을 변경
학생 설명·표시 public/app.js MODE_GUIDES, 단계 안내, scoreReceipt 확인
공용 화면 public/display.js 결과 공개·팀 합계·표시 메시지의 모순 확인
검사·설명서 test/, manual/ 기대 점수와 교사 안내를 함께 갱신

프론트와 서버가 공유하는 단일 모드 정의 모듈은 없습니다. 지금은 각 실행 환경의 정의를 함께 확인하는 것이 필요한 작업입니다. 문서화를 위해 새로운 프레임워크나 공유 계층을 추가하지 않았습니다.

4. 데이터 필드를 추가할 때의 체크리스트

  • createRoom/createRound/joinRoom 중 어디에 속하는 값인지 먼저 결정합니다.
  • 이전에 저장된 객체에는 필드가 없을 수 있습니다. 기존 값을 읽을 때의 기본값·검증을 마련합니다.
  • room.version 숫자가 있다고 자동 데이터 마이그레이션 코드가 동작하는 것은 아닙니다.
  • 원본에 저장하는 필드와 clientState/displayState로 공개할 필드를 따로 결정합니다.
  • 점수 합계·연결 여부처럼 계산할 수 있는 값을 별도로 중복 저장할 필요가 있는지 확인합니다.
  • 필드를 추가하는 일과 DO 클래스/namespace를 바꾸는 일은 다릅니다. 후자는 기존 데이터 접근에 더 큰 영향을 줄 수 있습니다.
  • 토큰·개별 비밀 선택·임무가 다른 학생 또는 TV 응답에 포함되지 않는지 검사합니다.

2. 치명적 — 조건이 맞으면 현재 데이터가 유실될 수 있음

C1. 진행 중 라운드에도 새 라운드 생성 요청을 받아 현재 상태를 교체함

  • 근거: game.js의 teacherAction('create_round') → createRound는 기존 라운드 종료 여부를 검사하지 않고 room.currentRound = round를 실행합니다.
  • 재현: 합성 방에서 투표 중 다시 create_round를 실행하면 이전 라운드 ID가 교체되고 이력은 0개로 남았습니다.
  • 영향: 아직 이력에 저장하지 않은 현재 표·예측·개인 내역을 잃을 수 있습니다. 교사 화면의 오래된 탭, 중복 요청, 재시도 등이 검토 대상입니다.
  • 범위: 유효한 교사 인증이 필요한 경로입니다. 인증 없이 아무나 관리자 기능을 실행할 수 있다고 확인한 것은 아닙니다. 정상 UI는 보통 진행 중 새 라운드 폼을 숨깁니다.
  • 수정 전 결정: 진행 중 생성 거절, 명시적 종료/교체 확인, 중복 생성 요청 처리 중 어떤 정책을 적용할지 정해야 합니다. 이번에는 구현하지 않았습니다.

실제 플랫폼 비밀키의 공개 소스 노출, 무인증 교사 action 실행, 현재 서비스 전체 실행 불가를 확인한 사실은 없습니다. 확인하지 못한 보안 침해를 치명적 결함으로 꾸며 적지 않았습니다.

3. 중요 — 오류·이탈·규칙 혼동 가능성

I1. 잠깐의 복원 요청 실패에도 입장 세션이 지워짐

  • 근거: app.js의 restore()는 GET state가 실패하면 오류 종류와 무관하게 saveSession(null)을 실행합니다.
  • 영향: 새로고침 시 일시적인 네트워크 오류도 재입장을 요구할 수 있습니다. 토큰을 잃고 이름으로 다시 들어오면 기존 학생과 별도 등록되어 점수가 분리되거나 명단이 늘어날 수 있습니다.
  • 확인 수준: 오류 분기는 코드로 확인했습니다. 특정 학교 기기의 실제 튕김 원인으로 확정하려면 해당 시점 네트워크/브라우저 기록이 필요합니다.
  • 수정 방향: 인증 만료와 일시적인 통신 실패를 구분하고 재시도 동안 세션을 유지하는 정책 검토.

I2. 1차 예측을 건너뛴 학생은 최종 예측 단계에서 첫 제출이 막힘

  • 근거: game.js의 submitPrediction()은 final_predict에서 current.initial이 없으면 거절합니다. 단계가 지나간 뒤 1차 예측을 제출하는 경로도 없습니다.
  • 재현: 1차 예측 없이 최종 단계로 진행한 합성 학생의 제출이 ‘먼저 1차 예측을 제출해 주세요.’로 거절됐습니다.
  • 영향: 자동 시간 진행·교사의 다음 단계 조작·통신 지연으로 1차 예측을 놓치면 남은 게임에 정상 합류하기 어렵습니다.
  • 정책 확인 필요: 최종 단계의 최초 제출을 허용할지, 관전으로 명시할지, 1차 예측 미제출자에게 사전 경고할지 결정해야 합니다.

I3. 일반 시민 역할의 이동 횟수 설명과 서버 제한이 다름

  • 근거: roleText('citizen')은 중간 신호 뒤 한 번 이동한다고 설명하지만, submitVote()의 revote 경로는 허용 역할에 대해 매 요청마다 최종 표를 갱신합니다.
  • 재현: 시민 역할 학생이 최종 선택 단계에서 세 번 다른 보기를 제출해 모두 수락됐습니다.
  • 영향: 설명을 따른 학생과 반복 변경한 학생이 서로 다른 규칙으로 게임했다고 느낄 수 있습니다.
  • 정책 확인 필요: 한 번 변경 제한을 구현할지, 시간 안에 계속 변경 가능하다고 안내를 맞출지 선택해야 합니다.

I4. 명단 삭제·활동 인원과 이미 제출한 표의 집계 범위가 다름

  • 근거: remove_player는 room.players만 삭제하고, countVotes()는 votes.first/final에 남은 표를 계속 셉니다. 연결 유예가 지나 활동 인원에서 빠지는 것도 표 삭제와는 별개입니다.
  • 재현: 두 학생이 표를 제출한 뒤 한 학생을 삭제하면 등록 1명·활동 분모 1명인데 집계는 2표로 남았습니다.
  • 영향: X 삭제를 ‘학생과 표를 모두 취소’로 기대하면 현재 동작과 다릅니다. 결과 표 수와 제출 진행률 분모를 비교할 때 혼동할 수 있습니다.
  • 정책 확인 필요: 제출한 표를 보존하는 선택 자체를 곧바로 버그로 단정하지 않습니다. 투표 공정성상 보존할 수도 있으므로 명단 정리와 표 무효화를 분리할지 먼저 정해야 합니다. 영향가 역할은 원래 한 학생이 2표 가중치를 갖는 별도 규칙입니다.

I5. 팀 공동 답은 마지막 제출이 덮어씀

  • 근거: submitTeamGuess()가 teamGuesses[player.team]에 새 객체를 대입하며 마지막 제출자 이름을 기록합니다.
  • 영향: 같은 팀 두 학생이 각자 오래된 폼을 수정하다 제출하면 나중 요청이 앞선 답을 교체합니다. 현재 UI에는 공동 답이 바뀐다는 안내가 있지만 버전 충돌 검사나 대표자 잠금은 없습니다.
  • 확인 수준: 저장 방식은 코드로 확인. 제품이 의도한 공동 편집 정책일 수 있으므로 팀 대표 제출·충돌 경고 필요성은 수업 방식에 따라 결정.

I6. 방의 수명과 결과 이력은 장기 성적 기록에 적합한 보관 구조가 아님

  • 근거: expire()의 방 저장소 삭제, currentRound 교체, finishRound()의 최대 20개 집계 요약. 개별 예측·점수 세부 내역을 매 라운드 영구 보관하지 않습니다.
  • 영향: 학생 누적 점수는 방에 남아도 ‘언제 어떤 이유로 몇 점을 받았는가’를 나중에 완전히 복원할 수 없습니다. 방이 만료되면 누적 점수도 함께 사라집니다.
  • 추가 차이: advanceRound()의 finished 도달은 finishRound()의 history 기록과 다른 경로입니다. 교사 응답의 최근 history는 현재 UI에도 표시되지 않습니다.
  • 정책 확인 필요: 일회성 수업용이면 허용할 수 있습니다. 장기 기록이 목적이면 보관 기간·내보내기·백업 정책을 별도로 정해야 합니다.

I7. 재연결 구현은 있지만 영구 오류와 반쯤 끊긴 연결의 구분이 약함

  • 근거: 두 클라이언트는 ping/pong, offline/online 처리, 재연결을 갖습니다. 그러나 pong 수신 지연을 감시하는 타임아웃은 없습니다.
  • 근거: 학생 앱은 소켓 종료 코드 4001을 세션 만료로 처리하지만, expire()는 1001로 닫습니다. 이후 방이 없다는 재연결 실패를 영구 오류로 구분하는 경로가 부족합니다.
  • 영향: 방 만료 뒤 재시도가 반복되거나, 학교 네트워크의 애매한 단절에서 연결 표시가 늦게 갱신될 가능성이 있습니다.
  • 확인 수준: 코드 경로는 확인했지만 실제 발생 빈도·기기별 증상은 운영 확인 필요입니다. 무료 호스팅 슬립이 원인이라고 단정할 수 없습니다.

I8. 세션 토큰 보관·PIN 노출·공개 정보의 경계

  • 근거: saveSession()은 토큰을 localStorage에 보관하고 connect()는 WebSocket URL query에 넣습니다. 교사 PIN 입력칸에는 type="password"가 없습니다.
  • 영향: 공유 PC의 남은 세션, 개발자도구·주소 로그·화면 녹화, 향후 스크립트 삽입 결함이 생길 때 인증정보가 노출될 위험이 있습니다. 현재 유출이나 스크립트 공격 성공을 확인한 것은 아닙니다.
  • 공개 데이터: 학생 상태 응답은 다른 학생 이름·팀도 포함하고, TV는 이름을 제거하지만 방 코드에 따른 학급명·교사명·공개 집계는 무인증으로 조회됩니다. 팀 합계는 비팀 모드의 응답에도 존재합니다.
  • 정책 확인 필요: 필요한 공개 범위, 공유 PC 로그아웃 안내, PIN 마스킹, 로그의 query 마스킹과 세션 보호 수준을 검토해야 합니다. 앱 PIN은 강한 학교 계정 인증을 대신하지 않습니다.

I9. 오류 처리 결과가 상위 폼 처리에 정확히 전달되지 않음

  • 근거: action()은 내부에서 오류를 toast로 표시한 뒤 정상 반환합니다. 상위 submit 처리기는 이후 formDrafts.delete()를 수행하므로 성공·실패를 구분하지 못합니다. 스킬·타이머 dialog도 요청 결과 전에 닫습니다.
  • 영향: 실패 때 성공 후 정리 절차가 실행될 수 있고 재시도 UX를 만들기 어렵습니다. 다만 화면의 값이 그대로 남아 다음 capture에서 회복되는 경우도 있어 모든 폼 입력이 즉시 사라진다고 단정하지 않습니다.
  • 확인 수준: 분기 구조 확인. 각 폼의 실제 입력 손실 조건은 추가 재현 필요.
  • 서버 쪽: 저장은 await persist() 뒤에 성공 응답하도록 되어 있고 예외는 오류 JSON으로 반환합니다. 저장 실패 처리가 아예 없는 구조는 아닙니다.

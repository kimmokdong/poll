## 2. 치명적 — 조건이 맞으면 현재 데이터가 유실될 수 있음

### C1. 진행 중 라운드에도 새 라운드 생성 요청을 받아 현재 상태를 교체함

- 근거: [game.js](../../src/game.js)의 `teacherAction('create_round') → createRound`는 기존 라운드 종료 여부를 검사하지 않고 `room.currentRound = round`를 실행합니다.
- 재현: 합성 방에서 투표 중 다시 `create_round`를 실행하면 이전 라운드 ID가 교체되고 이력은 0개로 남았습니다.
- 영향: 아직 이력에 저장하지 않은 현재 표·예측·개인 내역을 잃을 수 있습니다. 교사 화면의 오래된 탭, 중복 요청, 재시도 등이 검토 대상입니다.
- 범위: **유효한 교사 인증이 필요한 경로**입니다. 인증 없이 아무나 관리자 기능을 실행할 수 있다고 확인한 것은 아닙니다. 정상 UI는 보통 진행 중 새 라운드 폼을 숨깁니다.
- 수정 전 결정: 진행 중 생성 거절, 명시적 종료/교체 확인, 중복 생성 요청 처리 중 어떤 정책을 적용할지 정해야 합니다. 이번에는 구현하지 않았습니다.

실제 플랫폼 비밀키의 공개 소스 노출, 무인증 교사 action 실행, 현재 서비스 전체 실행 불가를 확인한 사실은 없습니다. 확인하지 못한 보안 침해를 치명적 결함으로 꾸며 적지 않았습니다.

## 3. 중요 — 오류·이탈·규칙 혼동 가능성

### I1. 잠깐의 복원 요청 실패에도 입장 세션이 지워짐

- 근거: [app.js](../../public/app.js)의 `restore()`는 `GET state`가 실패하면 오류 종류와 무관하게 `saveSession(null)`을 실행합니다.
- 영향: 새로고침 시 일시적인 네트워크 오류도 재입장을 요구할 수 있습니다. 토큰을 잃고 이름으로 다시 들어오면 기존 학생과 별도 등록되어 점수가 분리되거나 명단이 늘어날 수 있습니다.
- 확인 수준: 오류 분기는 코드로 확인했습니다. 특정 학교 기기의 실제 튕김 원인으로 확정하려면 해당 시점 네트워크/브라우저 기록이 필요합니다.
- 수정 방향: 인증 만료와 일시적인 통신 실패를 구분하고 재시도 동안 세션을 유지하는 정책 검토.

### I2. 1차 예측을 건너뛴 학생은 최종 예측 단계에서 첫 제출이 막힘

- 근거: `game.js`의 `submitPrediction()`은 `final_predict`에서 `current.initial`이 없으면 거절합니다. 단계가 지나간 뒤 1차 예측을 제출하는 경로도 없습니다.
- 재현: 1차 예측 없이 최종 단계로 진행한 합성 학생의 제출이 ‘먼저 1차 예측을 제출해 주세요.’로 거절됐습니다.
- 영향: 자동 시간 진행·교사의 다음 단계 조작·통신 지연으로 1차 예측을 놓치면 남은 게임에 정상 합류하기 어렵습니다.
- 정책 확인 필요: 최종 단계의 최초 제출을 허용할지, 관전으로 명시할지, 1차 예측 미제출자에게 사전 경고할지 결정해야 합니다.

### I3. 일반 시민 역할의 이동 횟수 설명과 서버 제한이 다름

- 근거: `roleText('citizen')`은 중간 신호 뒤 한 번 이동한다고 설명하지만, `submitVote()`의 `revote` 경로는 허용 역할에 대해 매 요청마다 최종 표를 갱신합니다.
- 재현: 시민 역할 학생이 최종 선택 단계에서 세 번 다른 보기를 제출해 모두 수락됐습니다.
- 영향: 설명을 따른 학생과 반복 변경한 학생이 서로 다른 규칙으로 게임했다고 느낄 수 있습니다.
- 정책 확인 필요: 한 번 변경 제한을 구현할지, 시간 안에 계속 변경 가능하다고 안내를 맞출지 선택해야 합니다.

### I4. 명단 삭제·활동 인원과 이미 제출한 표의 집계 범위가 다름

- 근거: `remove_player`는 `room.players`만 삭제하고, `countVotes()`는 `votes.first/final`에 남은 표를 계속 셉니다. 연결 유예가 지나 활동 인원에서 빠지는 것도 표 삭제와는 별개입니다.
- 재현: 두 학생이 표를 제출한 뒤 한 학생을 삭제하면 등록 1명·활동 분모 1명인데 집계는 2표로 남았습니다.
- 영향: X 삭제를 ‘학생과 표를 모두 취소’로 기대하면 현재 동작과 다릅니다. 결과 표 수와 제출 진행률 분모를 비교할 때 혼동할 수 있습니다.
- 정책 확인 필요: **제출한 표를 보존하는 선택 자체를 곧바로 버그로 단정하지 않습니다.** 투표 공정성상 보존할 수도 있으므로 명단 정리와 표 무효화를 분리할지 먼저 정해야 합니다. 영향가 역할은 원래 한 학생이 2표 가중치를 갖는 별도 규칙입니다.

### I5. 팀 공동 답은 마지막 제출이 덮어씀

- 근거: `submitTeamGuess()`가 `teamGuesses[player.team]`에 새 객체를 대입하며 마지막 제출자 이름을 기록합니다.
- 영향: 같은 팀 두 학생이 각자 오래된 폼을 수정하다 제출하면 나중 요청이 앞선 답을 교체합니다. 현재 UI에는 공동 답이 바뀐다는 안내가 있지만 버전 충돌 검사나 대표자 잠금은 없습니다.
- 확인 수준: 저장 방식은 코드로 확인. 제품이 의도한 공동 편집 정책일 수 있으므로 팀 대표 제출·충돌 경고 필요성은 수업 방식에 따라 결정.

### I6. 방의 수명과 결과 이력은 장기 성적 기록에 적합한 보관 구조가 아님

- 근거: `expire()`의 방 저장소 삭제, `currentRound` 교체, `finishRound()`의 최대 20개 집계 요약. 개별 예측·점수 세부 내역을 매 라운드 영구 보관하지 않습니다.
- 영향: 학생 누적 점수는 방에 남아도 ‘언제 어떤 이유로 몇 점을 받았는가’를 나중에 완전히 복원할 수 없습니다. 방이 만료되면 누적 점수도 함께 사라집니다.
- 추가 차이: `advanceRound()`의 finished 도달은 `finishRound()`의 history 기록과 다른 경로입니다. 교사 응답의 최근 history는 현재 UI에도 표시되지 않습니다.
- 정책 확인 필요: 일회성 수업용이면 허용할 수 있습니다. 장기 기록이 목적이면 보관 기간·내보내기·백업 정책을 별도로 정해야 합니다.

### I7. 재연결 구현은 있지만 영구 오류와 반쯤 끊긴 연결의 구분이 약함

- 근거: 두 클라이언트는 `ping/pong`, offline/online 처리, 재연결을 갖습니다. 그러나 pong 수신 지연을 감시하는 타임아웃은 없습니다.
- 근거: 학생 앱은 소켓 종료 코드 4001을 세션 만료로 처리하지만, `expire()`는 1001로 닫습니다. 이후 방이 없다는 재연결 실패를 영구 오류로 구분하는 경로가 부족합니다.
- 영향: 방 만료 뒤 재시도가 반복되거나, 학교 네트워크의 애매한 단절에서 연결 표시가 늦게 갱신될 가능성이 있습니다.
- 확인 수준: 코드 경로는 확인했지만 실제 발생 빈도·기기별 증상은 **운영 확인 필요**입니다. 무료 호스팅 슬립이 원인이라고 단정할 수 없습니다.

### I8. 세션 토큰 보관·PIN 노출·공개 정보의 경계

- 근거: `saveSession()`은 토큰을 localStorage에 보관하고 `connect()`는 WebSocket URL query에 넣습니다. 교사 PIN 입력칸에는 `type="password"`가 없습니다.
- 영향: 공유 PC의 남은 세션, 개발자도구·주소 로그·화면 녹화, 향후 스크립트 삽입 결함이 생길 때 인증정보가 노출될 위험이 있습니다. 현재 유출이나 스크립트 공격 성공을 확인한 것은 아닙니다.
- 공개 데이터: 학생 상태 응답은 다른 학생 이름·팀도 포함하고, TV는 이름을 제거하지만 방 코드에 따른 학급명·교사명·공개 집계는 무인증으로 조회됩니다. 팀 합계는 비팀 모드의 응답에도 존재합니다.
- 정책 확인 필요: 필요한 공개 범위, 공유 PC 로그아웃 안내, PIN 마스킹, 로그의 query 마스킹과 세션 보호 수준을 검토해야 합니다. 앱 PIN은 강한 학교 계정 인증을 대신하지 않습니다.

### I9. 오류 처리 결과가 상위 폼 처리에 정확히 전달되지 않음

- 근거: `action()`은 내부에서 오류를 toast로 표시한 뒤 정상 반환합니다. 상위 submit 처리기는 이후 `formDrafts.delete()`를 수행하므로 성공·실패를 구분하지 못합니다. 스킬·타이머 dialog도 요청 결과 전에 닫습니다.
- 영향: 실패 때 성공 후 정리 절차가 실행될 수 있고 재시도 UX를 만들기 어렵습니다. 다만 화면의 값이 그대로 남아 다음 capture에서 회복되는 경우도 있어 모든 폼 입력이 즉시 사라진다고 단정하지 않습니다.
- 확인 수준: 분기 구조 확인. 각 폼의 실제 입력 손실 조건은 추가 재현 필요.
- 서버 쪽: 저장은 `await persist()` 뒤에 성공 응답하도록 되어 있고 예외는 오류 JSON으로 반환합니다. 저장 실패 처리가 아예 없는 구조는 아닙니다.

## 4. 개선 — 유지보수와 설명을 명확하게 할 항목

| 항목 | 실제 근거 | 개선 방향 |
|---|---|---|
| 모드·단계·점수 설명이 여러 파일에 있음 | `game.js`, `app.js`, `display.js`, 설명서 | 규칙 변경 시 맞출 위치를 체크리스트로 유지. 필요할 때만 작은 단위로 정리 |
| 화면·입력·통신을 큰 파일 하나가 담당 | `app.js`의 화면 함수와 세션/폼/소켓 처리 | 수정 단위를 작게 나누고 영향 구역을 명시; 문서화를 이유로 전면 재구축하지 않음 |
| 오래된 테마 흔적 | 뒤쪽 CSS가 hero/mode/skill 배경과 TV 별 연출을 숨김 | 실제 화면·캐시 참조 확인 후 제거 후보 분리 |
| 안 보이는 자산도 사전 캐시 | `sw.js`에 atlas·hero 이미지 등록 | 완전 미사용으로 단정하지 말고 다운로드 필요성 검토 |
| 미연결 설정·API·화면 | `config.anonymous`, `set_team`, history UI | 유지 의도 확인 후 안내/연결/삭제 중 선택 |
| 발표자료 편집 API의 서버 없음 | 별도 슬라이드 HTML의 `/api/save-*`, `/api/upload-image` | 제작 도구 의존성을 발표자료 문서에서 명확히 표시 |
| 과거 저장 파일 제외 규칙 | `.gitignore`의 `/data/rooms.json`, 실제 저장 코드는 DO | 이전 구조의 흔적임을 설명. 현재 DB 위치로 오해하지 않도록 함 |
| 직접 의존성과 간접 의존성 구분 | 직접 devDependency는 Wrangler, lock에는 여러 도구 패키지 | lock에 있다는 이유만으로 미사용 라이브러리라고 삭제하지 않음 |
| 동점 결정 기준 | `orderedResults`는 동점이면 보기 label을 한국어 비교로 정렬 | 예측·소수파 승리 등 동점 정책을 학생 안내와 맞출지 확인 |
| 활동 인원과 방 정원 | `MAX_PLAYERS`는 등록 명단 50명을 기준으로 제한 | 오프라인 명단 누적 시 신규 입장 문제를 방 정리 정책에 반영 |
| 로컬 수정 반영과 배포 생성물 혼동 | dev의 최초 build가 `public`을 `.dist`에 복사 | 화면이 안 바뀌면 원본·출력 차이와 캐시부터 확인 |
| 실제 연결 통합 검사 부족 | 현 테스트는 소스·게임 엔진 중심 | Worker 저장·알람·WebSocket·여러 탭·동시 요청 검사 계획 필요 |

## 5. 질문한 점검 항목별 결론

| 점검 항목 | 조사 결론 |
|---|---|
| 프론트엔드 비밀키 하드코딩 | 실제 플랫폼 키 하드코딩은 발견하지 못함. 동적 세션 저장 위험은 I8 |
| DB 보안 규칙 | 별도 rules 파일은 없지만 서버 인증·명령 검증·DTO 필터가 경계 |
| 무인증 관리자 조작 | 교사 action에는 인증·역할 분리가 있음. 새 방 생성과 TV 조회가 공개인 것은 별도 정책 |
| 외부 API·하드코딩 주소 | 업무용 외부 API 없음. 프론트 API는 상대 경로/location 사용. `room.internal`은 내부 전달용 |
| 중복 API 호출 | HTTP 응답과 WebSocket으로 상태를 중복 수신할 수 있으나 곧 중복 저장을 뜻하지 않음. 매초 상태 조회 구조 아님 |
| 로딩·오류 처리 | action의 busy 방어와 toast, 연결 표시 있음. 모든 인증/폼 단계의 일관된 진행·실패 처리는 추가 확인 필요 |
| 저장 실패 | 서버가 저장을 await하고 실패 응답 처리. 사용자가 재시도하는 UI 경로는 I9 |
| 프론트/서버 책임 혼합 | 파일 경계는 분리됨. 규칙 설명·표시 조건이 여러 곳에 분산되어 어긋날 위험 존재 |
| 연결 해제 | 유예·재연결 구현 있음. 세션 삭제와 영구 오류 처리 문제는 I1/I7 |
| 여러 사용자의 수정 충돌 | 팀 마지막 제출 덮어쓰기는 확인. DO 전체 상태의 동시 요청 유실 여부는 단정하지 않음 |

Durable Object에는 플랫폼의 저장 일관성·실행 조정이 있으므로, 코드에 명시적 transaction이나 lock이 보이지 않는다는 이유만으로 동시 투표가 유실된다고 판정하지 않았습니다. HTTP body 읽기 등 비저장 await와 실제 동시 요청을 포함한 검사는 별도로 필요합니다. [Cloudflare 저장 API 설명](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)

## 6. 아직 확인되지 않은 사항

| 확인 필요 항목 | 현재 알 수 있는 것 | 추가로 필요한 증거 |

| Cloudflare 계정 요금제·사용량 | 플랫폼 종류와 코드 설정 | 계정 요금제·실제 사용량·제한·오류 로그 |
| 운영 백엔드 버전 | 공개 정적 파일 5개는 로컬과 일치 | 배포 메타데이터와 서버 코드 버전 비교 |
| 커스텀 도메인·스테이징 | `workers.dev` 공개 주소 응답 확인 | 계정의 도메인·route·별도 환경 설정 |
| 실제 교실 튕김 원인 | 재연결 코드의 약한 지점 | 발생 시각, 기기·브라우저, 네트워크/콘솔 기록; 비밀값 제거 후 조사 |
| 많은 기기의 동시성·성능 | 게임 엔진의 논리 검사 | 독립 세션 다중 연결·동시 투표·알람 경계 부하 검사 |
| 운영 데이터 백업·복구 | 앱 내 장기 내보내기/백업 구현 없음 | 플랫폼 측 백업·복구 가능 범위와 운영 정책 |

## 7. 후속 작업을 한다면

1. 진행 중 라운드 교체 방어와 임시 통신 실패 시 세션 유지처럼 데이터·재입장 위험부터 검토합니다.
2. 예측 미제출자의 다음 단계 참여, 시민 이동 횟수, 삭제된 학생의 표 처리 정책을 먼저 결정합니다.
3. 결정한 정책을 서버 규칙·학생 안내·TV·설명서·회귀 검사에 함께 반영합니다.
4. 실제 교실 규모의 독립 세션으로 재접속·동시 제출·타이머 경계를 검증합니다.
5. 운영 설정을 확인한 뒤 별도 요청에 따라 배포합니다. 이번 문서 생성은 배포를 수행하지 않았습니다.

전체 산출물 목차와 학습 경로는 [README](README.md), 변경 위치는 [수정 안내](modification-guide.md)를 참고하세요.
